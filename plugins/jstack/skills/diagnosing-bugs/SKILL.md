# 定位并修复 bug

## 硬性规则

- 先获取真实症状证据，再确认根因并修复。可以先读代码、配置和日志来建立复现；假设必须标明，不能凭源码推断就宣称根因已确认。
- 每一行发布的改动都要有运行时证据支撑。"也许有用"的防御代码不发布；证据推翻了某个猜想，就撤回它带来的改动。
- 展示命令、输出和抓取内容前，先把密钥、令牌、Cookie 替换成 `<REDACTED>`。
- 改任何文件之前（包括临时日志、测试程序和修复），按 [worktree](../worktree/SKILL.md) 的"开始"一节新建 worktree 和新分支。调用方给了已有 worktree 时，直接在其中工作。记下 worktree 绝对路径、新分支名和起点 commit。

## 流程

### 1. 建立反馈回路

按以下顺序尝试，选第一个能触达 bug 的方式：失败测试、对运行中服务的 HTTP 请求、带固定输入的命令行调用、无头浏览器脚本、回放抓到的请求或日志、最小化的临时测试程序、随机输入循环、二分脚本、新旧版本对比。各方式的做法和收紧方法见 [references/feedback-loops.md](references/feedback-loops.md)，在第一个方式行不通时读取。

复现由自己完成，不推给用户。先读用户提供的步骤描述、报错截图和录屏，从中提取操作步骤、输入数据和报错原文，再按上面的方式把它们变成可以自动运行的命令。

完成标准：能写出已经实际运行过的命令或可复验操作，并且满足：
- 走的是真实出错的代码路径，断言的是用户描述的那个症状，而不是"没崩溃"；
- 稳定问题能重复失败；偶发问题记录次数、失败率和触发条件，不能用一次成功证明修复；
- 优先使用快速、可重复运行的命令；无法自动化时记录实际操作、输入与运行证据，不用耗时或无人值守作为诊断的硬门槛。

### 2. 复现并缩小

运行回路，确认它失败的方式就是用户描述的症状，而不是附近另一个问题。然后逐项删减输入、调用方、配置和步骤，每删一项重跑一次，只保留删掉就不再失败的部分。

完成标准：剩下的每个要素都是必需的，并记录下准确的症状，包括报错原文、错误输出或耗时。

### 3. 提出猜想

已有直接证据时，写出因果链和能够确认或推翻它的检查。存在多个解释时，按可能性排列有证据依据的猜想，每个都给出可区分的预测；不凑数量。

完成标准：下一项检查能缩小不确定性，已说明依据和预期观察。

### 4. 埋点验证

每次只改一个变量，每个探针都对应某个猜想的预测。优先用调试器；其次在能区分不同猜想的边界处加日志。所有临时日志都加统一前缀，例如 `[DEBUG-a4f2]`，方便事后清理。性能问题先测基线，再二分定位，不靠日志猜。

完成标准：有运行时证据确认因果机制，不能仅凭其他猜想被排除就宣布根因。两次修复仍失败时重新检查共同前提、增加边界观测；第三次仍失败时交付复现、证据和已排除方案，停止盲目重试，供新上下文接手。

### 5. 写诊断结论

按 [references/report-template.md](references/report-template.md) 写三段：当前行为、期望行为、必须保持不变的行为。附上根因，以及第 1 步那条复现命令作为验收检查。

完成标准：三段都已写出，验收检查写成"`<命令>` → <期望结果>"的格式，并注明它目前是失败的。

用户只要求诊断、不要求修复时，到这里结束：交付诊断结论，删除临时日志和临时测试程序，按 [worktree](../worktree/SKILL.md) 的"清理"一节删除 worktree 和分支，不执行第 6、7 步。

### 6. 修复

1. 把缩小后的复现做成合适测试接缝上的失败测试。合适的接缝是指测试能重现 bug 在真实调用处的触发方式。如果找不到合适的接缝，就把这一点记为一项发现，写进收尾的"还有什么"。
2. 运行测试，确认它失败，并保存这段输出。
3. 保存失败输出，再做证据支持的修复；搜索同根因的调用点，清理被替代的代码和失效文档，保留有契约依据的兼容行为。
4. 重跑失败测试、第 1 步的原始场景及项目必过检查，确认通过并保存输出。线上 bug 和用户反馈应沉淀为可重跑的回归案例；无法自动化时保留操作步骤和原因。
5. 将通过验证的切片 commit，说明改动、验证和回滚方式，不逐次询问。用户限定仅诊断、仅本地修改或禁止提交时遵守范围；无提交时以明确 diff 交给 accept，不删除成果。

完成标准：拿到修复前失败、修复后通过的两段原样输出，并且原始场景不再复现。

### 7. 清理与交接

- 搜索调试前缀，删除所有临时日志；删除临时测试程序。
- 把正确的那个猜想写进修复的 commit 信息。
- 按 [references/report-template.md](references/report-template.md) 的"收尾"一节写汇报。
- 在 mode 中：把汇报、验收检查和"必须保持不变的行为"返回给 bug-fix playbook，到此结束。
- 单独使用时：读取 [finish](../finish/SKILL.md) 并照做，传入 worktree 绝对路径、新分支名、起点 commit、汇报，验收检查是复现命令加"必须保持不变的行为"里能运行的检查。

完成标准：搜索调试前缀没有结果；汇报已返回给 bug-fix playbook，或 finish 的每一步都已完成。

## 示例

用户说："导出 CSV 时偶尔丢最后一行，帮我修一下。"

执行：
1. 写一个导出 1001 行数据的测试，循环跑 50 次，丢行率 40%，确认复现。
2. 缩小到"最后一批不足缓冲区大小"这一个条件。
3. 列出 3 个猜想，埋点后确认根因是关闭流前没有刷新缓冲区。
4. 写出诊断结论，保存失败输出；修复后重跑通过，将测试和修复一起 commit。
5. 贴出 50 次中失败 20 次、修复后 50 次全部通过的两段输出，执行 finish，独立验收 PASS 后自动开 PR，pr 确认 READY 后按收尾规则清理 worktree。

结果：诊断结论加经过验证的 commit，落在保留下来的新分支上，并告诉用户分支名。验收检查为"`npm test -- export.spec.ts` → 50 次全部通过"。

## 常见问题

现象：试遍所有方式都建不出能失败的回路。
原因：缺少能复现问题的环境、数据或权限。
处理：交付已有症状证据、尝试过的方式和缺少的环境、数据或权限。允许继续只读缩小范围，但将未证实的原因标为假设，不宣称修复成功。

现象：回路失败了，但失败方式和用户描述的不同。
原因：触发的是附近的另一个问题。
处理：回到第 1 步，把断言收紧到用户描述的那个具体症状。

现象：修复后测试通过，但原始场景仍然能复现。
原因：测试接缝太浅，没有重现真实的触发链路。
处理：以原始复现命令的结果为准，回到第 4 步，并把"接缝太浅"写进收尾的"还有什么"。
