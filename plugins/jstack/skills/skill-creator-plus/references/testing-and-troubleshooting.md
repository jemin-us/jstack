# 测试与排错

第 5 步写测试、审查时定位问题时读取本文件。先用一个有难度的任务反复迭代到跑通，把有效做法写进 skill，再扩大测试范围。

## 触发测试

```
应触发：
- <最直接的说法>
- <换一种说法>
- <带具体参数的说法>
不应触发：
- <无关话题>
- <相邻 skill 的典型说法>
```

目标是相关说法有九成左右能自动加载。

在 Claude Code 中确认模型实际看到的 description，以及手动调用的 skill 没有进入列表：

```bash
claude -p "不要调用任何工具。原样输出你 skill 列表里 <skill 名> 的 description；列表里没有就回答没有。"
```

测试插件里尚未发布的 skill 时，加 `--plugin-dir <插件目录>` 从源码加载。

## 功能测试

按"前提、动作、预期"三段写用例，覆盖正常产出、工具调用成功、出错时的处理和边界情况：

```
前提：项目名"四季度规划"，5 条任务描述
动作：执行 skill 流程
预期：项目已创建；5 条任务属性正确并关联到该项目；没有接口错误
```

## 效果对比

同一个任务分别在开启和关闭 skill 时执行，比较对话轮数、澄清次数、失败调用次数和 token 消耗。

## 按模型测试

skill 的效果取决于运行它的模型，在计划使用的每个模型上都测一次，关注点不同：

| 模型 | 看什么 |
|---|---|
| 能力较弱、速度快的模型 | 指引够不够，有没有因为缺步骤而做错 |
| 能力最强的模型 | 有没有过度解释；删掉某段后行为不变，就删掉 |

## 排错

| 现象 | 原因 | 处理 |
|---|---|---|
| 该加载时没加载，用户只能手动点名 | description 太宽泛，或缺少用户会说的关键词 | 补充关键词。向模型提问"什么情况下你会使用 <skill 名>？"，对照回答补上漏掉的场景 |
| 无关请求也加载 | 范围过大 | 写边界说明；补充具体的系统名或文件类型 |
| 触发后不按指令执行 | 正文过长、约束离执行它的步骤太远、措辞含糊 | 精简正文；把约束移到执行它的那一步；改用脚本检查 |
| 某个 `references/` 文件只读了开头 | 它是从另一个 references 文件链接过去的，模型只预览了前几十行 | 改为从 `SKILL.md` 直接链接 |
| 结果每次不一样 | 步骤没有完成标准，或完成标准无法检查 | 把完成标准改成可检查的状态 |
| MCP 调用失败 | 未连接、认证过期或工具名写错 | 先不用 skill，单独调用一次该 MCP；工具名区分大小写 |
| 响应变慢或质量下降 | `SKILL.md` 过大，或同时启用的 skill 太多 | 细节移到 `references/`；同时启用的 skill 不超过 20–50 个 |
