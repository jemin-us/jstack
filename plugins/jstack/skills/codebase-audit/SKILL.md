# 审计代码结构

找出一块代码的结构问题，交付一份按修法组织的清单：每个修法可以单独交给 mode 去做，能配检查的交给 [codebase](../codebase/SKILL.md) 固定下来。向用户提问按 [harness](../harness/SKILL.md)。

## 硬性规则

- 只读。不修改、不新建项目里的任何文件；审计结果写在回复里，用户指定文件时才写文件。

## 流程

### 1. 定范围并运行现有检查

范围是一个目录或模块，加上它导入的代码和导入它的代码。用户没有给范围时，问用户。

运行项目已有的检查命令（lint、架构检查、类型检查），记下每条的结果。有基线文件时，数出属于本范围的条目。命令跑不起来时记下原因，不安装依赖。

完成标准：能说出范围包含哪些文件、每条现有检查的结果或跑不起来的原因、本范围占基线几条。

### 2. 找问题

通读范围内的代码，按自己的判断列出结构问题。然后专门再查两类，它们在通读时容易漏：

- **同一个事实写了多份。** 逐项对照范围内的代码和它的上游定义（schema、API client、共享常量、兄弟模块）：数量上限、枚举值列表、正则和键的拼接格式、字段之间的对应关系、URL 参数名、查询或请求的固定选项、错误码。每找到一个字面量或约定，搜索它在别处有没有第二份。
- **没有被引用的代码。** 对范围内的每个导出和每个文案键搜索引用；项目有检查未用导出的工具时用它。

每个问题写一行：编号、`文件:行号`（多处时全部列出）、一句话。按代码注释或合同是有意为之的，另列为"不改"并写出依据。

同时核实已被替代的旧 API、一次性兼容层和失效示例。搜索无引用只是线索，删除建议须排除动态调用、对外导出和明确兼容契约。

完成标准：上面两类各有搜索结果（找到的问题，或"搜索了哪些项，没有第二份"）；每个问题都带 `文件:行号`。

### 3. 定修法

把问题归并成修法，一个修法是一次能单独提交的改动。每个修法写五项：

| 项 | 写什么 |
|---|---|
| 解决 | 问题编号 |
| 范围 | 本范围内，或全仓；涉及的文件数（估计值注明是估计） |
| 改行为 | 否，或是哪一处用户可见的行为会变 |
| 检查 | 修完后用什么防止它再出现：已有的检查命令和它会消掉的基线条目；或要新加的规则，写出工具和规则内容；或"不能"，写出原因 |
| 回归 | 这次改动要碰的行为，现有哪些测试覆盖；没有测试覆盖的分支逐条列出 |

修法必须改掉问题本身。只让检查通过而依赖关系不变的做法不算修法：把目录挪到检查不看的位置、缩小检查范围、往基线加条目。

以下问题不配修法，列进"不改"并写明条件：目前触发不了、要等某个条件出现才成立的隐患；修它需要的改动比问题本身大的。

排序：不改行为且在本范围内的排前面；改行为的其次；全仓的排最后并注明要单独立项。

完成标准：每个问题要么属于一个修法，要么在"不改"里有依据；每个修法五项齐全。

### 4. 汇报

````markdown
**现有检查**
- <命令>：<结果>；基线里本范围 N 条

**问题**
- P1 `<文件:行号>` <一句话>

**修法**
### F1 <一句话>
- 解决：P1、P4
- 范围：本范围，约 3 个文件
- 改行为：否
- 检查：<工具和规则> | 已有 `<命令>`，消掉基线 N 条 | 不能，<原因>
- 回归：<覆盖它的测试>；没有覆盖：<分支>

**不改**
- P9 <依据或条件>

**不确定**
- <看到了什么不一致，还差什么才能下结论>

**下一步**
- 修法逐个交给 mode；"检查"一栏要新加的规则交给 codebase
````

证据等级按项目约定标注；没有运行的结论写明来自读代码。

## 示例

用户说："帮我审计一下 `billing/` 这个模块，看结构上有什么问题。"

执行：范围是 `billing/` 的 7 个文件、它导入的 `orders/` 和 `shared/`、导入它的 2 个接口文件；`make lint` 通过，`make test` 里的分层检查失败，失败的 2 条都不在本范围，基线里本范围 4 条；通读列出 9 个问题；对照 `shared/schema.py` 又找到重试次数上限 3 在两个文件里各写一份、发票状态列表手写了一份而 schema 已导出，搜索导出找到 1 个没有引用的函数；归并成 5 个修法，例如"状态列表和上限改为引用 `shared/schema.py`，检查：在分层检查脚本里加一条，禁止 `billing/` 出现这两个字面量"；一个只在将来支持多币种时才会出错的金额取整列进"不改"。

结果：回复里是一份清单，5 个修法各有五项，其中 3 个能配检查；没有改动任何文件。

## 常见问题

现象：想到的修法是把目录移到另一个 feature 下面，基线条目就消失了。
原因：检查按目录名判断，移动后它不再看这些导入，依赖关系没有变。
处理：不列为修法。改成让被依赖的代码下沉到公共位置，或经对方的入口文件导入。

现象：范围很大，通读不完。
原因：范围超过了一次审计能读完的量。
处理：告诉用户读了哪些、没读哪些，建议按子目录分次审计；不对没读的部分下结论。

现象：一个修法的"检查"一栏只能写"不能"。
原因：规则需要判断，无法机械匹配。
处理：照实写"不能"和原因，不为了有检查而写一条匹配不准的规则。
