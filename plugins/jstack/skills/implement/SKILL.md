# 实现

按 ticket 或用户的明确描述编写代码，测试先行，完成后 commit 到项目内 worktree 的新分支。

## 硬性规则

- 用户明确要求仅本地修改或禁止提交时，完成实现和自检，按明确 diff 调用 accept；不执行提交、PR 和会删除未提交成果的清理。受权限限制时保留成果并报告，不把未交付写成完成。
- 不修改已有测试来让检查通过，不放宽断言、不跳过测试、不扩大超时。确实需要修改已有测试时，按第 7 步在提交信息里写明。

## 流程

### 1. 读取输入

- 给了 ticket 编号：运行 `gh issue view <编号> --json number,title,body,comments`，读全文。开工前先说明"正在实现 #<编号> <标题>"。
- 没有 ticket：以用户的描述为准。描述含糊时，向用户提问；自动执行或作为 subagent 执行时不提问，按最保守的理解实现，并在收尾写明所做的假设。写代码前，派一个 subagent 写验收检查，派法按 [harness](../harness/SKILL.md)：brief 里只放用户的原话和仓库路径，不放自己的实现思路，要求它读相关代码后返回 1–3 条"命令或操作 → 期望结果"，重构时返回已有测试的命令。

完成标准：能说出要交付的行为、至少一条验收检查、约束和不做的范围。

### 2. 建 worktree

按 [worktree](../worktree/SKILL.md) 的"开始"一节新建 worktree 和新分支。调用方给了基准分支和分支名时照用；给了已有 worktree 时直接在其中工作。

完成标准：记下 worktree 绝对路径、新分支名、起点 commit，之后每条命令都在 worktree 里执行。

### 3. 确定接缝

接缝是观察行为的公开边界，测试只写在接缝上。按以下顺序确定：

1. ticket 的"上下文"或所属 spec 的"测试接缝"写了接缝，直接采用。
2. 没写时，从实际调用方选择能覆盖交付行为的公开边界，复用已有检查。只有不同选择会改变验收目标、且现有证据不能决定时才问用户。
3. 局部文案、样式等不适合新增自动化测试的改动，采用能复验的实际操作；浏览器效果用浏览器验证。说明检查覆盖什么，不为满足流程增加只复述实现的测试。

完成标准：写下本次要测试的接缝清单，接缝越少越好。

### 4. 判断是否为重构

如果本次改动不应改变行为（重构、搬移、改名），动结构前先确认：

1. 找到覆盖被移动行为的已有测试，运行并确认通过。
2. 覆盖不到的行为，先补一条测试并确认通过，再动结构。
3. 类型检查和 lint 不算覆盖。

完成标准：每一段要移动的行为都有一条能通过的测试。

### 5. 红绿循环

每一轮做一个可验证的切片。新增或修复行为有合适测试路径时：

1. 在一个接缝上写一条测试，运行并确认失败，而且失败原因是行为缺失，不是语法或导入错误。
2. 写刚好让它通过的代码，运行并确认通过。
3. 运行改动相关的类型检查和单个测试文件。

下一轮的测试根据上一轮学到的东西再写，不要先把所有测试写完。拿不准一条测试是否值得保留时，读取 [references/testing.md](references/testing.md)。

完成标准：交付行为有运行证据，适用的测试和类型检查通过；未使用自动化测试的检查方式及理由已记录。

切片完成时检查实际调用方：删除被替代的旧实现、未用导出、重复规则、无意义包装及失效的示例或文档。检查同根因的其他调用点并一起修复。保留有公开契约依据的兼容行为；超出本次目标的结构问题交给维护流程，不混入无关重写。优先用共享实现、类型和检查防止问题再出现。

### 6. 运行验收检查和项目检查

1. 按 ticket 顺序逐条运行验收检查，记下实际输出。
2. 运行项目规定的必过检查及改动相关测试。影响共享模块、依赖或跨模块契约时运行全量测试；否则记录所选范围和依据。检查失败时查根因，不扩大 timeout 或放宽断言。

完成标准：每条验收检查与期望一致，适用的项目检查通过。不一致时按"常见问题"处理；未运行的检查不能写成通过。

### 7. 提交

1. 用 `git status` 和 `git diff` 确认只包含本次改动，不提交无关文件。
2. 在 worktree 里 commit 到新分支，不逐次询问。有 ticket 时，提交信息写明 ticket 编号。提交说明写清行为变化、验证方法和回滚方式。修改了已有测试时，在提交信息里逐个写明被改的测试文件和理由，accept 从提交信息读取这些理由；明确禁止提交时，在传入的 diff 说明里记录同样信息。

完成标准：worktree 里 `git status` 干净，`git log -1` 显示本次提交。

### 8. 写汇报

按以下三段写，每个论断标明"已运行""推断"或"未验证"：

```markdown
**改了什么**
- 改动的行为和主要文件，commit 哈希
- worktree 绝对路径、新分支名、起点 commit

**验证了什么**
- 验收检查 1：`<命令>` → 实际输出（已运行）
- 项目检查和测试范围：通过 / 失败 / 受阻 / 未运行，附依据
- 清理了哪些旧路径、同类问题；哪些兼容行为有契约依据

**还有什么**
- 修改过的已有测试及理由
- 所做的假设、选定的接缝（作为 subagent 执行时）
- 第 2 步发现的遗留 jstack worktree
- 没有 ticket 时写：验收检查由 subagent 按用户描述写出
```

完成标准：三段都已写出。

### 9. 交接

- 由 mode 派发时（brief 中写明）：把汇报返回给 mode，到此结束。验收、清理和开 PR 由 mode 负责。
- 单独使用时：读取 [finish](../finish/SKILL.md) 并照做，传入 worktree 绝对路径、新分支名、起点 commit、验收检查和上一步的汇报。

完成标准：汇报已返回给 mode，或 finish 的每一步都已完成。

## 示例

用户说："实现 #42"

执行：读取 #42，验收检查是 `curl -s localhost:3000/health` → `OK`；建 worktree `.claude/worktrees/jstack-health-check` 和分支 `jstack/health-check`；在路由层写一条健康检查测试，确认失败；实现接口，测试通过；运行验收检查得到 `OK`；全量测试通过；commit；执行 finish，独立验收 PASS 后自动开 PR，当前 HEAD 的 CI 通过后清理 worktree。

结果：汇报 commit 哈希、验收检查的实际输出 `OK`、accept 结论 PASS、PR 和 CI 结果，告诉用户分支 `jstack/health-check` 已保留，"还有什么"写"无"。

用户说："把 formatPrice 从 utils 挪到 money 模块"

执行：建 worktree 和新分支；判定为重构；确认已有的 formatPrice 测试通过；搬移并更新调用方；测试仍通过；全量测试通过；commit；执行 finish 完成独立验收、PR 和 CI 跟进。

结果：汇报中注明验收检查由 subagent 写出（已有的 formatPrice 测试命令），附上 accept 结论和保留的分支名。

## 常见问题

现象：验收检查跑不通，但实现看起来正确。
原因：期望结果写错，或依赖的环境（服务、网络、浏览器）不可用。
处理：不改写验收检查，也不改代码去迎合错误的期望。停止提交，在汇报中贴出实际输出，标为"失败"或"受阻"，说明原因。

现象：新测试一写就通过。
原因：行为已经存在，或测试没有测到目标行为。
处理：检查断言是否真的依赖本次要实现的行为；确认行为已存在时，在汇报中写明，不重复实现。

现象：为了让检查通过，似乎必须修改已有测试。
原因：需求改变了既有行为，或已有测试测的是实现细节。
处理：确认属于前者时可以修改，并在 commit 信息里写明理由；属于后者时，改写为接缝上的行为测试，同样写明。无法判断时不改测试，停止提交并汇报，按 FAIL 处理。

现象：全量测试有失败，但与本次改动无关。
原因：仓库原本就存在失败。
处理：在改动前的基线上运行同一测试确认，确认是原有失败后在汇报中列出，不修复、不跳过。
