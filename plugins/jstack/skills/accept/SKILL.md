# 独立验收

## 硬性规则

- 一条检查通过与否，由没写这段代码的 subagent 判定。主 agent 可能就是作者，只能把结果改得更严，不能把"失败"或"受阻"改成"通过"。
- PASS/PASS+NOTES 必须有实际独立执行者标识、交付的任务范围和返回结果记录。作者换角色自评、空 agent 列表或只有 wait 调用均不是独立验收；无法取得这些证据时记 BLOCKED。
- 验收只报告，不修代码。作者自检、独立验收和用户验收分别汇报，不能互相替代。
- 一次交付最多三轮审查。后续轮次检查新 diff、上轮问题和受影响的回归；证据只对它覆盖的代码版本有效：新 diff 或共享契约变化影响到的检查都要重跑，界面改动包括受影响的页面状态、视口和交互；其余检查沿用记录。

## 流程

### 1. 收集输入

需要三样东西：

1. **验收范围**：commit 范围（如 `<base>..HEAD`），或调用者明确给出的 diff。调用方传入时用传入的；用户直接调用时，默认取当前分支相对仓库默认分支的范围（默认分支用 `git symbolic-ref --short refs/remotes/origin/HEAD` 查出），记录该范围；仅当存在多个会改变验收对象的候选范围时向用户澄清。
2. **验收检查**：
   - 有 ticket 时，运行 `gh issue view <编号> --json title,body` 读取 `## 验收检查` 一节。
   - bug-fix 场景：取 diagnosing-bugs 产出的复现命令，以及"必须保持不变的行为"。
   - 用户直接给出的检查，原样使用。

检查默认均为必需项；仅当项目或用户事先明确为补充项时才可标为非阻断，不因运行失败或受阻而降级。

3. **启动和操作方式**：查找项目里的 `verify-<app>` skill，位置是 `.agents/skills/verify-*/` 或 `.claude/skills/verify-*/`。有就把它的 `SKILL.md` 路径带上；没有就跳过。

完成标准：手上有确定的验收范围，以及至少一条验收检查。一条都没有时，停下来向用户要，不自己编。

### 2. 派 subagent 执行 brief

按 [references/brief.md](references/brief.md) 填好 brief，派一个 subagent 执行。subagent 怎么派，按 [harness](../harness/SKILL.md) 中当前 Harness 的一列来。

关键：brief 里放验收范围、验收检查、轮次、前轮发现及可沿用证据和 `verify-<app>` 路径；无提交时附测试修改理由。不放作者的思路、实现说明和自评，以免验收者沿着作者的假设去验证。

完成标准：已记录独立执行者标识、调用及返回证据，返回内容包含逐条检查、代码质量和测试修改结果。没有独立渠道或没有返回记录时停止判 PASS，报告 BLOCKED。

### 3. 核对 subagent 的结果

逐行核对运行证据和独立审查发现；代码质量问题必须有具体位置、违反的契约或多余结构及影响，不接受个人风格偏好：

1. 每行都有实际执行的命令和输出。缺的退回 subagent 补跑；仍然拿不到的，改记"失败"，注明"无法判定"。
2. "通过"的行：实际执行的命令或操作与验收检查写的一致，或写明了替换的理由。不一致又没有理由的，退回 subagent 按原检查重跑。
3. "失败"的行：复跑它的命令。这次通过的仍记"失败"，注明"不稳定"，附上两次的输出。
4. 运行 `git diff --numstat <范围>`，确认删除行数大于 0 的测试文件都列在"测试改动"里，删除行数为 0 的不列。漏掉的文件，用 `git log <范围> -- <文件>` 查提交信息后补上；未提交范围改用工作区 diff、未跟踪文件及调用方提供的修改理由。

完成标准：结果表的每一行都核对过，没有一行从"失败"或"受阻"变成"通过"。

### 4. 给出结论

| 结论 | 条件 |
|---|---|
| PASS | 所有必需检查通过，无阻断性审查发现和未说明理由的测试改动，无补充备注 |
| PASS+NOTES | 同 PASS 的必需条件，但有事先指定的非阻断补充项或备注 |
| BLOCKED | 无已确认失败，但必需检查或独立审查因环境、权限或工具缺失而无法完成 |
| FAIL | 必需检查失败、有证据充分的阻断性审查发现，或已有测试被删改却没说明理由 |

同时存在失败和受阻时给出 FAIL，并分别列出。BLOCKED 不算通过，调用方保留现场，不盲目重试或合并。

按下面的格式回复：

```markdown
## 结论：PASS | PASS+NOTES | BLOCKED | FAIL

验收范围：<base>..<完整 head SHA>
证据覆盖：<实际代码版本、输入和环境；未提交时记录 diff 快照>
独立执行者：<标识、任务调用和返回记录位置；缺失则 BLOCKED>

| # | 验收检查 | 结果 | 证据 |
|---|---|---|---|
| 1 | `<命令>` → <期望> | 通过 / 失败 / 受阻 | <实际输出摘录；受阻写缺什么> |

测试改动：无 / <文件> 已说明理由 / <文件> 未说明理由

审查发现：位置、问题、证据、影响、是否阻断。
失败或受阻详情：每条写复跑命令、实际输出和期望，或缺少的条件。
```

## 示例

**示例 1：mode 验收一张 ticket**

mode 传入 ticket #42 和范围 `a1b2c3..d4e5f6`。读出两条验收检查，派 subagent 执行。subagent 报告第 1 条通过，第 2 条 `curl localhost:3000/api/orders?status=paid` 返回 500。主 agent 复跑后同样得到 500。结论为 FAIL，附上命令和响应体，交回 mode。

**示例 2：用户验收一次 bug 修复**

用户说"验收一下刚才的修复"。取当前分支相对 `main` 的范围并记录。验收检查是 diagnosing-bugs 给出的复现命令 `pnpm test src/cart.test.ts -t "空购物车"`，加上一条保持不变的行为"非空购物车结算金额不变"。两条都通过，但 diff 修改了 `src/cart.test.ts` 里一条已有断言，commit 信息里也没说明理由。结论为 FAIL。

## 常见问题

现象：验收检查依赖一个本地没在运行的服务。
原因：项目没有 `verify-<app>`，或者服务没启动。
处理：有 `verify-<app>` 就按它的启动步骤运行；没有就把该条标为"受阻"，并在结论里建议运行 jstack skill create-verify-app。

现象：找不到 ticket 里的 `## 验收检查` 一节。
原因：ticket 不是 `tickets` 生成的，或者被手动改过。
处理：向用户要验收检查，不要从 ticket 正文里猜。
