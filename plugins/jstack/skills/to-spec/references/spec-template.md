# spec 模板

生成 spec 时读取本文件。issue 标题用中文，正文按下面的章节顺序书写，章节不增不减。

```markdown
## 问题与目标
用户看到的现象，解决后的样子。

## 行为
1. 当 <条件> 时，系统应 <行为>
2. ……

## 实现决策
- <决定>：<理由>

## 测试接缝
在哪一层测，复用哪类已有测试。

## 不做
明确排除的范围。

## 待定
无
```

## 各章节要求

同一内容只写在一个章节，其他章节需要时引用行为编号，例如"见行为 2"。

| 章节 | 要求 |
|---|---|
| 问题与目标 | 两三句，从用户视角写，不写实现原因 |
| 行为 | 每条一句"当…时，系统应…"；覆盖主路径和关键边界，不追求穷举；每条都能被验证 |
| 实现决策 | 只写从代码和配置里查不到的决定及其理由；按推荐答案定、用户没有确认过的决定，在决定后标"（假设）"；不写文件路径、代码片段，以及发布规则、版本号这类仓库已有约定 |
| 测试接缝 | 优先用已有接缝；层级越高越好；接缝越少越好，理想是一个 |
| 不做 | 至少写一条；讨论中被否决的方向写在这里 |
| 待定 | 发布时必须写"无" |

## 多仓库时

| 仓库 | 额外要求 |
|---|---|
| 后端 | "实现决策"写完整 API 契约：路径、请求、响应、错误码 |
| 前端 | "实现决策"不重复契约，写"API 契约见 <后端 spec 的 issue 链接>" |
