# 需求追问

## 硬性规则

- 只追问，不动手：本 skill 不写代码、不写 spec、不发 issue。

## 流程

### 1. 摸清现状

读用户的描述，以及它涉及的代码和文档。列出这次需要做的决定，并按依赖关系排好：哪些决定必须先定，后面的决定才能讨论。

完成标准：已经列出第一轮可以问的问题，即所有前置条件都已经明确的决定。

### 2. 查事实

事实自己查，决策交给用户：某个问题依赖环境里的事实时，例如现有代码怎么写、某个工具支持什么、配置是什么，就自己查。查询量大时，派 subagent 执行 brief 去查。不要等查询结果：只有依赖这个事实的问题需要等，其他问题照常在本轮提出。

完成标准：本轮要问的问题里，没有哪个是能查到答案却拿去问用户的。

### 3. 提出一轮问题

把本轮可以问的问题一次列完，依赖其他未决问题的留到后面的轮次。每个问题都给出推荐答案，措辞要让用户回答"同意"就等于采纳推荐。按下面的格式输出，然后停下来等用户回答：

```markdown
❓ **Q1** - **<问题标题>**：<问题内容，可以包含选项和取舍>

➡️ <推荐答案>

---

❓ **Q2** - **<问题标题>**：<问题内容>

➡️ <推荐答案>
```

自动执行时只问一轮，并且只问同时满足两条的决定：从仓库里查不到、运行一下也看不出答案；选错后要迁移数据、改对外接口、删除数据，或要返工一张以上的 ticket。其余决定直接采用推荐答案，记为假设。没有需要问的决定时不提问，直接进入第 5 步。

完成标准：每个问题都有编号和推荐答案；本轮没有夹带依赖其他未决问题的问题。

### 4. 根据回答重新计算

用户回答后，把已定的决定记下来，再判断哪些问题因此可以问了，作为下一轮。用户推翻了之前的决定时，把受影响的问题重新加回待问列表。查到的新事实和之前的决定矛盾时，在下一轮明确指出矛盾，请用户决定。

完成标准：下一轮的问题列表已经算好；如果已经没有可问的问题，进入第 5 步。

### 5. 收尾

所有问题都问完之后，按决定逐条汇总，请用户确认双方理解一致。用户确认后，提示下一步调用 jstack skill `spec`，把结论写成 spec。

自动执行时不等确认：列出已定的决定和记为假设的决定，交给下一步。

完成标准：用户明确确认了汇总内容；自动执行时，决定和假设都已列出。

## 示例

用户说："我想给订单列表加导出功能，帮我想清楚。"

执行：
1. 读订单列表的代码，查到它已经支持筛选和分页。
2. 第一轮提出三个问题：导出格式（推荐 CSV）、导出范围是当前筛选结果还是全部订单（推荐当前筛选结果）、数据量很大时同步还是异步导出（推荐先查现有订单量再定，同时派 subagent 去查）。
3. 用户回答后，第二轮只问因此可以问的问题，例如异步导出时完成通知怎么发。
4. 问完后逐条汇总，用户确认。

结果：得到一份已确认的决定清单，提示用户下一步调用 `spec`。

## 常见问题

现象：用户回答"不知道"或"你定"。
原因：这个问题需要的信息用户也没有，或者用户认为不重要。
处理：采用推荐答案并标明"按推荐处理"，在收尾汇总里列出，方便用户回头修改。

现象：用户在追问过程中要求直接开始实现。
原因：用户认为需求已经够清楚。
处理：汇总当前已定和未定的决定。未定项由用户决定是否按推荐处理，然后结束追问，提示用户下一步调用 `spec`。
