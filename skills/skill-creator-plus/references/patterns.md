# 正文模板与常见写法

搭正文章节时读取模板；流程的形状拿不准时读取"五种常见写法"。

## 正文模板

````markdown
# <技能标题>

## 硬性规则
- <不属于任何单一步骤的约束；没有就不写这一节>

## 流程

### 1. <第一步>
具体动作，包括这一步专属的约束。
```bash
python3 scripts/<脚本>.py --input <文件>
```
完成标准：<做完后的状态>

### 2. <第二步>
……

## 示例
用户说："新建一个营销活动"
执行：1. 查询已有活动；2. 按给定参数创建
结果：活动已创建，并返回链接

## 常见问题
现象：<错误信息>
原因：<为什么出现>
处理：<怎么修复>
````

## 五种常见写法

| 写法 | 适用场景 | 关键做法 |
|---|---|---|
| 顺序流程 | 多个步骤必须按固定顺序执行 | 写明顺序和依赖；每步校验；写出失败后的回滚方式 |
| 多工具协同 | 流程跨多个服务或 MCP | 按阶段拆分；写明阶段之间传递的数据；进入下一阶段前先校验；集中处理错误 |
| 迭代打磨 | 产出需要多轮修改才能达标 | 写明质量标准；用脚本校验；循环修复；写明何时停止 |
| 按情况选工具 | 同一目标在不同情况下用不同工具 | 给出判断条件；写明备选方案；向用户说明选择原因 |
| 领域规则 | 除了调用工具，还需要专业判断 | 先检查后执行；用条件分支写清处理路径；留下审计记录 |

## 让约束被执行

约束靠具体程度起作用，不靠强调词。按以下顺序选写法：

1. 结果确定的检查写成脚本。代码的结果是确定的，自然语言的理解不是。
2. 写不成脚本的，列出具体的检查项：

   ```
   调用 create_project 前确认：
   - 项目名不为空
   - 至少指派一名成员
   - 开始日期不早于今天
   ```

3. "关键：""不要跳过"这类强调只在实际运行中观察到约束被漏掉时才加，并且只加在被漏掉的那一条上。
