# frontmatter 与 description

## 最小格式

```yaml
---
name: 技能名
description: 当任务涉及 <关键词> 时使用。
---
```

## 全部字段

| 字段 | 必填 | 规则 |
|---|---|---|
| `name` | 是 | kebab-case，与文件夹名一致，不含 `claude`、`anthropic` |
| `description` | 是 | 不超过 1024 字符，不含 `<`、`>`；写清触发场景和边界 |
| `license` | 否 | 开源时填写，例如 `MIT`、`Apache-2.0` |
| `compatibility` | 否 | 1–500 字符，说明运行环境要求，例如依赖、网络、适用产品 |
| `allowed-tools` | 否 | 限制可用工具，例如 `"Bash(python:*) WebFetch"` |
| `metadata` | 否 | 自定义键值，常用 `version`、`author` |

frontmatter 会进入系统提示词，因此禁止以下内容：

- 尖括号；
- 可执行代码；
- 保留词命名。

## description 写法

句式：

```
当任务涉及 <关键词>、<关键词> 时使用。<相邻场景> 使用 <其他 skill>。
```

写作要点：

- 关键词取自用户的原话：动作、对象、系统名、文件类型。
- 只在术语、产品名、文件名处保留英文。
- 有相邻 skill 时，写一句边界说明。
- 不写实现方式、价值描述、修饰语。

### 好的例子

```
当任务涉及 PostgreSQL 建模、表结构设计、DDL、迁移方案、数据字典或 ER 图时使用。
```

```
当用户要求审查 Shop4 Web 的变更、PR、模块或页面时使用。开发自检使用 shop4-web-development。
```

```
当任务涉及 Figma 设计稿解析、组件规格整理或设计交接文档时使用。
```

### 差的例子

| 写法 | 问题 |
|---|---|
| `帮助处理项目。` | 太宽泛，无法判断何时触发 |
| `构建一套完善的多页面文档体系。` | 只写了功能，没写触发场景 |
| `实现带层级关系的 Project 实体模型。` | 写的是实现细节，用户不会这么说 |
| `处理文档。` | 范围太大，容易误触发；应收窄为“审查 PDF 合同” |
| `当用户 asks for design specs 时使用。` | 中英混排 |

## 调试触发

向 Claude 提问：

```
什么情况下你会使用 <skill 名>？
```

Claude 会复述它对 description 的理解。对照回答：漏掉的场景补成关键词，多出来的场景写进边界说明。
