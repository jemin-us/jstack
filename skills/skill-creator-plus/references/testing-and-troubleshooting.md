# 测试与排错

先用一个有难度的任务反复迭代，直到能跑通，再把有效做法写进 skill，然后扩大测试范围。

## 1. 触发测试

```
应触发：
- <最直接的说法>
- <换一种说法>
- <带具体参数的说法>
不应触发：
- <无关话题>
- <相邻 skill 的典型说法>
```

目标是相关说法有九成左右能自动加载。准备 10–20 条说法，统计其中多少条能自动加载、多少条需要手动点名。

## 2. 功能测试

按“前提、动作、预期”三段写测试用例：

```
前提：项目名“四季度规划”，5 条任务描述
动作：执行 skill 流程
预期：项目已创建；5 条任务属性正确并关联到该项目；没有接口错误
```

测试要覆盖以下情况：

- 正常产出
- 工具调用成功
- 出错时的处理
- 边界情况

## 3. 效果对比

同一个任务分别在开启和关闭 skill 时执行，比较以下指标：

- 对话轮数
- 澄清次数
- 失败调用次数
- token 消耗

同一请求跑 3–5 次，检查输出结构是否一致。再看新用户第一次使用时，是否只需少量引导就能完成。

## 排错

| 现象 | 原因 | 处理 |
|---|---|---|
| 提示 `Could not find SKILL.md` | 文件名大小写不对 | 改名为 `SKILL.md` |
| 提示 `Invalid frontmatter` | 缺少 `---`，或引号未闭合 | 修正 YAML 后重新校验 |
| 提示 `Invalid skill name` | `name` 含空格或大写字母 | 改为 kebab-case |
| 从不自动触发 | description 太宽泛，或缺少用户会说的关键词 | 补充关键词；用“什么情况下你会使用”调试 |
| 无关请求也触发 | 范围过大 | 写边界说明；补充具体的系统名或文件类型 |
| 触发后不按指令执行 | 正文过长、关键约束靠后、措辞含糊 | 精简正文；关键约束提到开头；改用脚本检查 |
| MCP 调用失败 | 未连接、认证过期或工具名写错 | 先不用 skill，单独调用一次该 MCP；工具名区分大小写 |
| 响应变慢或质量下降 | SKILL.md 过大，或同时启用的 skill 太多 | 细节移到 `references/`；正文控制在 5000 词以内；同时启用的 skill 不超过 20–50 个 |

## 上线后迭代

| 问题 | 信号 | 处理 |
|---|---|---|
| 触发不足 | 该加载时没加载，用户手动启用 | 在 description 中补充关键词和术语 |
| 触发过度 | 无关请求也加载，用户把它关掉 | 在 description 中补充边界说明，收窄范围 |
| 执行不稳定 | 结果不一致，调用失败，用户需要纠正 | 改进指令，补充出错时的处理方式 |

每次修改后升级 `metadata.version`。
