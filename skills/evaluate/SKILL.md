# 技能行为评测

## 流程

### 1. 确定实验

先读 [references/running.md](references/running.md)。选择用例、客户端、重复次数和源码路径；使用同一任务比较变体时固定输入与判定标准，记录版本和配置差异。判定标准不给候选，候选只看正常任务描述。模型和客户端版本由实际工具记录，不写死厂商模型名。

完成标准：候选任务、比较对象和独立判据已确定；没有把测试目标写进候选任务提示。

### 2. 执行

运行本 skill 的 `scripts/run.py`。每次创建独立 Git 仓库，将技能源码加载为项目技能；默认不接触真实远端、凭据或业务数据。脚本使用客户端现有登录，不读取或输出凭据。客户端缺失、认证失败、超时分别留下结果，不能冒充行为通过。

执行者也可以按脚本生成的 workspace/prompt 手动运行，但必须记录真实客户端、完整工具记录和最终 diff；手动运行不能标记为自动客户端验证。CLI 的源码加载验证不等于已安装插件的自动触发验证。只读场景禁止修改；所有内置场景禁止提交、push 和外发，这是评测隔离边界，不改变正式开发默认交付。

完成标准：每次都有独立工作区、客户端信息、事件日志、最终回复、Git 差异和客观检查结果。

### 3. 独立判定

脚本核对事件中的独立执行者和完成记录；修改类任务缺少证据即 BLOCKED，不能由候选自述补足。识别到独立执行只证明另一执行者完成过任务，仍须核对其任务确为验收。脚本根据实际产物和外部检查输出 `FAIL`、`BLOCKED` 或 `NEEDS_REVIEW`，不会仅凭进程成功或最终回复输出 PASS。非作者 subagent 读取去掉客户端标签的任务、diff、客观结果和工具记录；必要时重跑，给出 PASS / FAIL / BLOCKED。确认失败来自技能、实现、评测工具还是环境，不能用改判据掩盖真实失败。

检查工具记录能否证明执行了所需步骤、只读与本地边界是否保持、用户看到的行为是否正确。浏览器要求必须有实际浏览器证据；服务请求必须有真实响应。CI 用例只模拟本地 CI 失败处理，不证明真实 GitHub 交付。

完成标准：每个 PASS 都能指向运行证据和独立判定；报告中分开列脚本测试、静态审查和客户端实测。

### 4. 比较与交付

同一代表任务至少运行三次；计划支持的每个客户端分别运行。汇总完成率、失败类别、额外提问、用时和 token（客户端未提供时写未知）。比较旧版和新版时，判断者只看匿名标签；只跑一个变体不能声称改进幅度。保留失败样本和证据，清理前确认它们仍在。

完成标准：交付结果目录、各场景状态、未运行项和是否建议发布；不能运行的客户端明确标为 BLOCKED，不用模拟客户端代替实测。

## 示例

改了排查流程：运行已有 401 场景三次，独立检查真实 HTTP 响应、代码差异及工具记录。客户端缺失的另一端标 BLOCKED；不能因为 Python 判据通过就声称双端技能有效。

## 常见问题

最终回复说“全通过”，但事件记录没有运行检查：保持 NEEDS_REVIEW，由独立者复跑并判定流程偏差。进程超时留下的代码可以用于诊断，但这次运行仍是 BLOCKED。
