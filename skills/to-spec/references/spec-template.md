# spec 模板

生成 spec 时读取本文件。issue 标题用中文，正文按下面的章节顺序书写，章节不增不减。

```markdown
## 背景
用户遇到什么问题、现在的症状。从用户视角写。

## 方案
用户视角下问题怎么被解决。

## 行为
1. 当 <条件> 时，系统应 <行为>
2. ……

## 实现决策
- 涉及的模块与接口
- API 契约、数据结构、关键交互

## 测试接缝
在哪一层测，复用哪类已有测试。

## 不做
明确排除的范围。

## 待定
无
```

## 各章节要求

| 章节 | 要求 |
|---|---|
| 背景 | 写用户看到的现象，不写实现原因 |
| 方案 | 写用户能感知的变化，不写代码结构 |
| 行为 | 每条一句"当…时，系统应…"；覆盖主路径和关键边界，不追求穷举；每条都能被验证 |
| 实现决策 | 不写文件路径和代码片段；原型中提炼出的类型或状态机可以保留，并注明出自原型 |
| 测试接缝 | 优先用已有接缝；层级越高越好；接缝越少越好，理想是一个 |
| 不做 | 至少写一条；讨论中被否决的方向写在这里 |
| 待定 | 发布时必须写"无" |

## 多仓库时

| 仓库 | 额外要求 |
|---|---|
| 后端 | "实现决策"写完整 API 契约：路径、请求、响应、错误码 |
| 前端 | "实现决策"不重复契约，写"API 契约见 <后端 spec 的 issue 链接>" |
