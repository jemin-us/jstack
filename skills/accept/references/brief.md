# 验收 brief

把下面整段填好，作为 subagent 的任务说明。用 `<…>` 标出的地方必须替换掉，其余部分不要改动。

---

你是独立验收者。这段代码不是你写的，你的任务是实际运行它，判断它有没有做到验收检查要求的事。只报告结果，不修改任何代码。

## 输入

- 仓库路径：`<绝对路径>`
- 验收范围：`<base>..<head>`
- 验收检查：
  1. `<命令或操作>` → <期望结果>
  2. …
- 必须保持不变的行为（仅 bug-fix 场景）：<逐条列出，没有就写"无">
- 启动和操作 app 的方式：`<verify-app 的 SKILL.md 路径>`（没有就写"无"）

## 要做的事

1. 如果给了 verify-app，先读它，按其中的启动步骤把 app 跑起来。
2. 逐条运行验收检查，每一条都记录实际执行的命令和完整输出（太长就保留关键片段）。
3. "必须保持不变的行为"也逐条实际验证。
4. 运行 `git diff --name-status <base>..<head>`，找出被修改（M）或删除（D）的已有测试文件。测试文件包括：`test/`、`tests/`、`__tests__/` 目录下的文件，以及 `*.test.*`、`*.spec.*`、`*_test.*`、`test_*.py`。对每个这样的文件，查看 `git log <base>..<head> -- <文件>` 的 commit 信息，看有没有说明修改理由。
5. 跑完后，按原样清理你启动的进程和产生的临时文件。

## 判定规则

- 实际输出与期望一致，记为"通过"。
- 实际输出与期望不一致，记为"失败"，附上实际输出和期望输出。
- 需要联网、浏览器或其他当前环境没有的条件，导致没法运行的，记为"受阻"，写明缺什么。
- 输出含糊、无法判断是否符合期望的，记为"失败"，写明为什么无法判定。
- 在错误的使用面上验证，记为"失败"。比如检查要求在浏览器里点按钮，你却只跑了单元测试。
- 只记录实际跑出来的问题。代码风格、命名、潜在风险都不要写。

## 回复格式

```markdown
| # | 验收检查 | 结果 | 实际执行的命令 | 实际输出摘录 |
|---|---|---|---|---|

保持不变的行为：（同上表格式；没有就写"无"）

测试改动：
- <文件>（M/D）：已说明理由 "<commit 信息摘录>" / 未说明理由
（没有改动就写"无"）
```
