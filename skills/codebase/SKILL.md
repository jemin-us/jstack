# 固定代码基准

把项目的形状规则落成会失败的检查，让违规在改动的当下被拦住，不靠事后读代码和重构来恢复。向用户提问、项目指令文件是哪个，按 [harness](../harness/SKILL.md)。

## 硬性规则

- 本 skill 只立检查，不改业务代码。已有违规进只减不增的基线；维护流程调用时，返回后由 mode 继续清理和交付，不把冻结违规当作维护完成。
- 不为了让检查通过而放宽规则、往基线里加条目或删除检查。

维护已有基线时先移除本次已修复的条目，并核对前后数量；不为通过 CI 新增豁免。定期清理由 [mode](../mode/SKILL.md) 的维护流程串起审计、重构和验证，不在这里创建定时任务。

## 流程

### 1. 判断用法并摸清现状

用法有三种：

| 用法 | 情况 |
|---|---|
| 接入 | 项目已有代码，规则没有检查或只有一部分有 |
| 起步 | 新项目，用户给出参照项目或规则 |
| 加规则 | 用户指出一类反复出现的错误，或刚修掉一类问题 |

然后查三样东西：CI 配置里实际运行的检查命令；写着规则的文档（项目指令文件、README、架构文档）；已有的检查和基线文件。运行一次现有的检查命令。

现有检查命令在动手前就失败时，把失败内容列给用户，问是修掉还是写进基线；自动执行时两样都不做，在汇报开头写明，然后继续。

完成标准：能说出 CI 运行哪条命令、哪些规则已有检查、哪些只有文字，以及现有检查命令的运行结果。

### 2. 定规则

每条规则写成一句话，并带出处。出处只有三种：

- **接入**：规则文档里写明的。文档没有规则时，从目录结构和导入方向归纳候选规则，列给用户确认；自动执行时只采用现有违规不超过 5 处的候选，记为假设。
- **起步**：参照项目的规则文档和它的检查实现（lint 配置、架构测试）。逐条换成目标语言的说法；目标项目用不上的列出来，不搬。
- **加规则**：这类错误已经出现过的一处，写出 commit、`文件:行号` 或用户纠正时的原话。

两种情况不自己定：文档的一句话有两种读法，或文档和现有代码冲突。把两种读法和各自会判为违规的位置列给用户；自动执行时取判出违规更少的读法，记为假设。

没有出处的规则不加。动态导入、反射这类绕过手段，项目里没出现过就不加限制。

完成标准：每条规则都有一句话和出处；有歧义的规则都已由用户回答或记为假设。

### 3. 选强制方式

每条规则按顺序取第一个可行的：

1. lint 规则、架构测试或检查脚本，报错写明文件、行号、违反的规则和改法。
2. 类型或编译期约束。
3. 测试。
4. 文字规则。只用于需要判断、无法机械检查的规则，并写明为什么无法检查。

加规则时，先看能不能改结构让这类错误写不出来：用单一来源代替手工同步的列表，删掉同一件事的第二种做法，让内部实现无法从外部导入。能就把它作为建议写进汇报，由用户决定是否另开改动；本次仍按上面的顺序立检查。

工具用项目已经在用的。项目没有时用该语言常用的依赖检查工具；不能安装依赖时，用该语言的标准库写检查脚本。

完成标准：每条规则都标了强制方式和所用工具。

### 4. 实现检查并冻结已有违规

1. 在未改动的代码上运行新检查，得到已有违规的清单。
2. 把清单写进基线文件。检查在两种情况下失败：出现基线之外的违规；基线里的某条已不再出现（提示删除这一条）。这样基线只减不增。
3. 运行检查，确认在当前代码上通过。

起步时没有已有违规，不建基线文件。

完成标准：检查在当前代码上通过；业务代码相对起点没有改动（`git diff --stat` 只有检查、配置、基线和文档）。

### 5. 证明检查会失败

每条检查各做一次：临时写入一处违规，运行，确认失败且报错指向这一处，然后撤回。加规则时写回的是第 2 步那处真实出现过的旧写法。

完成标准：每条检查都有一段失败输出；撤回后 `git status` 里没有残留。

### 6. 接进 CI

把新检查接到 CI 已经在运行的那条命令上。CI 没有运行任何检查命令时，在 CI 配置里加一步，并在汇报里单独写明改了 CI 配置。

然后只读查询合并目标分支的保护设置（`gh api repos/<仓库>/branches/<分支>/protection`），确认运行这条检查的 CI job 是不是必过检查。不是时，在汇报里写出把它设为必过检查的命令。改仓库设置会影响所有协作者：只有用户看过这条命令并明确同意后才执行，自动执行时不执行。

完成标准：能指出 CI 配置里运行这条检查的文件和行号；能说出运行它的 job 当前是不是必过检查。

### 7. 登记规则

在项目指令文件里维护一张规则表，每条规则一行。规则的细节只写在检查的配置里，表里不重复。

```markdown
| 规则 | 由什么强制 | 基线 |
|---|---|---|
| api 只导入 service | `make test`（`tests/test_layering.py`） | `tests/layering-baseline.json`，3 条 |
| 金额不用浮点数 | 无，靠评审 | — |
```

加规则时先查表：这条规则已在表里而强制一栏是"无"，说明文字没有管住它，本次必须升到检查。

完成标准：第 2 步的每条规则在表里都有一行。

### 8. 汇报

```markdown
**立了什么**
- 规则表

**验证了什么**
- 每条检查的失败输出（已运行）
- CI 配置里运行它的文件和行号（已运行）

**还有什么**
- 基线条目数，以及清理它们可以交给 mode
- 假设和留给用户的问题
- 必过检查的现状，和要用户同意后才执行的命令
- 起步时没有搬的参照规则
```

## 示例

用户说："这个项目的分层老是被改乱，帮我固定下来。"

执行：判断为接入；CI 运行 `make test`，README 写了四层的依赖方向，没有任何检查；定出 4 条规则，其中"api 只调用 service"有两种读法（是否允许导入 shared），问用户后取允许；项目不能装依赖，用标准库写 `tests/test_layering.py`；在原代码上跑出 3 处违规，写进 `tests/layering-baseline.json`；临时加一处 store 导入 service，`make test` 失败并指到这一行，撤回；`make test` 已在 CI 里，不改 CI 配置；在 `AGENTS.md` 里加规则表。

结果：`make test` 通过，业务代码没有改动，基线 3 条；汇报里写明分支保护要用户在仓库设置里开。

用户说："手工拼查询 key 这个错我第二次纠正了，固定下来。"

执行：判断为加规则；出处是 `list.tsx:149` 的字面量 key；规则表里没有这条；项目已有 eslint，用 `no-restricted-syntax` 禁止 key 工厂之外出现 `queryKey: [` 字面量；已有 6 处写进基线；写回 `list.tsx:149` 的旧写法，eslint 报错，撤回；eslint 已在 CI 的 `check` 里。

结果：规则表多一行，基线 6 条；汇报建议另开改动把 key 全部收进工厂。

## 常见问题

现象：归纳出的规则在现有代码上有几十处违规。
原因：它可能不是这个项目真正遵守的规则。
处理：不采用，列进汇报的"留给用户的问题"；用户确认它确实是规则时，再全部冻结进基线。

现象：新检查让 CI 时间明显变长。
原因：检查扫描了依赖目录或构建产物。
处理：把扫描范围限定在源码目录；仍然慢时在汇报里给出耗时，由用户决定是否保留在每次提交都跑的命令里。

现象：检查通过，但用户指出的那类错误仍然能写出来。
原因：检查的匹配条件比规则窄。
处理：回到第 5 步，用用户指出的那处写法做失败证明，直到它被拦住。
