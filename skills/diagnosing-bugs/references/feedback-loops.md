# 建立反馈回路

第 1 步中，第一个尝试的方式行不通时读取本文件。

## 可选方式

大致按以下顺序尝试：

1. **失败测试**：在能触达 bug 的任意测试接缝上写测试，单元、集成、端到端都可以。
2. **HTTP 请求脚本**：用 `curl` 或脚本请求运行中的开发服务，断言响应。
3. **命令行调用**：用固定输入调用，把输出和已知正确的快照做 diff。
4. **无头浏览器脚本**：驱动页面，断言 DOM、控制台或网络请求。
5. **回放现场数据**：把真实的请求、载荷或事件日志存到磁盘，单独送进出错的代码路径。
6. **临时测试程序**：只启动系统的最小子集，例如一个服务加模拟依赖，用一次函数调用触发 bug。
7. **随机输入循环**：针对"有时输出错误"的 bug，跑上千组随机输入，找出失败的模式。
8. **二分脚本**：bug 出现在两个已知状态之间（commit、数据集、版本）时，把"切到状态 X、检查"写成脚本，交给 `git bisect run`。
9. **对比运行**：同一输入分别跑新旧两个版本或两套配置，对比输出。
10. **人工协助脚本**：最后才用。复制 `scripts/hitl-loop.sh`，用它引导人按步骤操作，并收集结果。

## 收紧回路

拿到一个能跑的回路后，继续收紧：

- **更快**：缓存准备工作，跳过无关的初始化，缩小测试范围。
- **更准**：断言具体症状，而不是"没崩溃"。
- **更稳**：固定时间、固定随机种子、隔离文件系统、断开外部网络。

一个 30 秒还时好时坏的回路，几乎等于没有；一个 2 秒、结论稳定的回路才算合格。

## 偶发 bug

目标是提高复现率，不是追求一次干净的复现。可以循环触发上百次、并行运行、增加负载、缩小时间窗口、注入等待。复现率 50% 的 bug 可以调试，1% 的不行，要一直提高到可以调试为止。

## 性能退化

日志通常帮不上忙。先建立基线测量（计时脚本、性能分析器、查询计划），再二分定位。先测量，后修复。
