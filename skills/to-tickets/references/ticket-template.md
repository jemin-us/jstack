# ticket 模板

在第 5 步写 ticket 正文时读取本文件。标题用中文，说明交付什么，不写在正文里。

```markdown
## 目标

完成后，端到端能用的行为是什么。从用户视角写，不按层列实现步骤。

## 上下文

- 所属 spec：#<编号>
- 涉及模块：<模块名，用 GLOSSARY 中的术语>
- 入口文件：`<路径>`（仅作提示，以实际代码为准）
- 相关已有测试：`<路径或测试名>`
- 已定的实现决策：<从 spec 中摘出与本 ticket 相关的部分>

## 约束

- 不改动已有测试来让验收通过；确需修改的，在收尾时说明理由
- <本 ticket 不做的范围>

## 验收检查

1. `<命令或操作>` → <期望结果>
```

## 写法要求

- **自包含**：不写“见上文讨论”“如前所述”。用到的决策直接摘进“上下文”，不要只给 spec 链接。
- **路径只是提示**：入口文件路径可能过时，执行者以实际代码为准。不写代码片段。原型里提炼出的类型或状态机可以摘录，并注明来源。
- **验收检查**：
  - 写 1–3 条，每条都能直接运行，并且能明确判断通过或失败。
  - 优先写“改动前失败、改动后通过”的检查，例如新增的测试命令。
  - 需要操作界面时，写清操作步骤和应该看到的结果。
  - 不写“功能正常”“体验良好”这类无法判定的描述。
- **阻塞关系不写进正文**：阻塞关系用 GitHub 原生的 dependency 表达，发布时设置。

## 示例

```markdown
## 目标

用户在结算页输入有效优惠码后，订单总价按优惠规则减少，并在价格明细中显示优惠金额。

## 上下文

- 所属 spec：#12
- 涉及模块：订单、优惠码
- 入口文件：`src/order/checkout.ts`（仅作提示）
- 相关已有测试：`src/order/checkout.test.ts`
- 已定的实现决策：优惠码只作用于商品小计，不作用于运费

## 约束

- 不改动已有测试来让验收通过；确需修改的，在收尾时说明理由
- 不做优惠码的后台管理

## 验收检查

1. `npm test -- checkout.test.ts -t "优惠码"` → 新增用例全部通过，改动前这些用例失败
2. `npm test` → 全部通过
```
