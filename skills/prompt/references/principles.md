# 原理

写指针、步骤或修剪时遇到拿不准的情况，读本文件。各节按流程顺序排列。

## 指针

指针是一直留在 agent 上下文里的一句话，指向上下文之外的内容，并写明什么时候去读。skill 的 description 是指针，`CLAUDE.md` 里"改部署脚本时读 docs/deploy.md"这一行也是。

agent 会不会去读，取决于指针的措辞，而不是被指向内容的重要程度。重要内容放在一句含糊的指针后面，等于让执行结果随机。先把措辞改准；改准了仍然不读，才把内容搬回正文。

指针一直占着上下文，所以比正文更要精简：

- 最能触发的词放最前面。
- 一条分支只写一个触发词。几个同义词描述的是同一条分支，合并成一个。
- skill 的 description 用一句话写它做什么，不展开正文里的介绍。

## 两种负担

- **上下文负担**：一直加载的内容（description、`CLAUDE.md` 的每一行）每一轮都占 token 和注意力，不管用不用得上。
- **认知负担**：人要记住有哪些文档、何时用哪个。这份负担换来的是人的控制权，该由人判断的地方就让人记，不需要人判断的地方就交给指针。

放到指针后面的内容，只付出指针那一行的上下文负担；完全没有指针的内容，全靠人记。

## 信息层级

内容按 agent 需要它的紧迫程度分三层：

1. **正文里的步骤**：agent 按顺序做的事，最优先。
2. **正文里的参考**：按需查阅的规则。一组平级的规则放在同一层是正常的。
3. **移出去的参考**：放在单独文件，靠指针读取，可以是同目录的文件，也可以是任何地方的外部文档。

往下移得太少，正文臃肿；移得太多，agent 需要的内容被藏起来。这一层取舍就是全部决策。

- **渐进披露**：把内容移到下一层，目的是保护层级、让正文好读，省 token 是附带的。判断标准是分支：每条分支都要用的留在正文，只有部分分支用到的移出去。有步骤的文档里堆着本该移出去的参考，会把步骤埋起来，agent 是否注意到步骤就变成了碰运气。
- **就近放置**：一个概念的定义、规则和例外放在同一个标题下，读到一部分就能顺带读到其余部分。好的文档读起来像专门写给 agent 的说明书。分散和重复不同：重复是同一意思写两遍，分散是一个意思被拆到多处。
- **臃肿**：每一行都有用、也不重复，文档仍然可能太长。注意力会被稀释，每多一行就多一行要维护。解决办法还是分层：把参考移到指针后面，按分支或顺序拆开，让每条路径只带自己需要的内容。

## 完成标准

每个步骤以完成标准结尾。它有两个属性：

- **清晰度**：agent 能不能分清做完和没做完。"已理解需求"这类模糊标准会让 agent 提前结束，注意力被后面可见的步骤吸走。先改准标准，这是最便宜的办法；标准确实无法改准、又观察到 agent 赶进度时，才把后面的步骤拆开隐藏。拆开只有跨过真正的上下文边界才有效，例如交给 subagent 或下一个会话；在同一个会话里调用，后面的步骤仍在上下文中。
- **要求程度**："每个改动的模型都已列出"比"列出改动"逼出更彻底的工作。要求程度决定 agent 做多少功课，而且不限于步骤："每条规则都已检查"同样约束一组平级的参考规则。

最好的完成标准既能检查，又要求穷尽。

## 何时拆分

把一份文档拆成两份会付出两种负担之一，只在值得时拆：

- **按顺序拆**：后面的步骤诱使 agent 赶完眼前这一步时，把后面的步骤移到别处。反过来，把两段流程合并，会让前一段的每一步都看到后面的步骤，更容易提前结束。
- **按调用方式拆**：只适用于 skill，见 [skill-mechanics.md](skill-mechanics.md)。

## 引导词

引导词是模型预训练里已有的紧凑概念，agent 执行时会拿它来思考，例如"红绿循环""战争迷雾""曳光弹"。把同一个词反复写，不换说法，它就能用很少的 token 稳定一整片行为。自造的新词也能用，但要写定义，等于用 token 换来预训练白给的东西，所以先找现成的词。

引导词在两处起作用：在正文里，agent 每次看到它都会做同样的事；在指针里，同一个词出现在你的 prompt、文档和代码里，agent 更容易把它们联系起来，找到对应内容。

找机会用引导词替换啰嗦的写法：三处都写着"快、确定、开销小"，可以收成一个"紧"字（紧的回路）；"一个你信得过的回路"可以换成"红"，把模糊的关口变成能观察的状态：回路在这个 bug 上变红，或者没有。

中文里优先选模型熟悉的中文工程用语；技术术语保留英文原文，见 [chinese.md](chinese.md)。

## 否定

靠禁令引导行为，会把被禁止的行为带进上下文，反而让它更容易出现。正向写出目标行为，例如"注释写一行"，被禁止的行为就不必出现。只有无法正向表达的硬性底线才写成禁令，而且要同时写出该做什么。

## 修剪

- **单一事实来源**：每层意思只写在一处，改行为时只改一处。重复浪费 token，还会抬高这层意思的显眼程度。引导词是有意重复一个词，不是重复一层意思。
- **不缓存环境**：`package.json` 的脚本、配置文件、目录结构、`--help` 输出本身就是事实来源。文档复述它们就成了缓存，只有查找成本很高时才值得。只写查不到的：未成文的约定、决策的理由、配置里看不出的坑。
- **相关性**：每一行是否还和文档要做的事有关。一行会因为从来不相关（纯铺垫、本该移出去的分支）或过时而失去相关性。没有修剪纪律，文档会积成沉积层：过时内容一层层压着，因为加东西感觉安全、删东西感觉危险。
- **no-op**：模型默认就会做的事，写出来只占位置。检验标准是"删掉后行为变不变"，这取决于模型而不是读者，有分歧时实际运行一次来判断。不通过就整句删掉，不要只删几个字。这个检验也适用于引导词：一个词弱到盖不过默认行为（agent 本来就算认真时写"要认真"），换一个更强的词。
