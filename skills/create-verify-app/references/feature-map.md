# 功能清单格式

建 `features/` 目录时读这份文件。功能清单是这个项目的验证依据：一个功能如果有多个入口，只验证其中一个不算完整的证明。

## features/index.md

索引文件，包含三部分：

1. **基线前提**：启动地址、一次性的数据目录、预置数据、自检必须通过的条件。
2. **操作约定**：
   - 每个功能都从基线状态开始，命令按原样执行。
   - 修改过的数据要恢复。
   - 被跳过的入口不能写成"已通过另一条路径验证"。
3. **功能列表**：每行一个链接，并用一句话说明这个功能覆盖了什么。

## 每个功能文件

先写一个一级标题，再用一段话描述用户能看到的行为。之后按顺序写四个二级标题：

1. `子功能`：每行写一个短 ID 和一句说明。
2. `入口`：从用户视角列出所有进入方式。
3. `操作步骤`：先写"前提："，再逐条写，每条都包含用户动作、对应的命令、可观察的结果。
4. `注意事项`：容易浪费时间或让验证失效的坑。预置数据缺少前提导致路径失败的，原因也写在这里。

不写实现细节。只写用户路径、稳定标识、所需状态、命令和可观察的证据。

## 示例：features/create-note.md

```markdown
# 新建笔记

用户可以在浏览器或 CLI 里保存一条带标题的笔记，可以放弃未保存的草稿，并能从另一个视图确认笔记已经保存。

## 子功能

- `create-save`：保存标题和正文。
- `create-cancel`：放弃浏览器里的草稿。
- `create-cli`：在终端里新建同样结构的笔记。

## 入口

- 浏览器工具栏里的"新建笔记"按钮。
- 焦点不在输入框时按 `n` 键。
- 终端运行 `notes create --title 标题 --body 正文`。

## 操作步骤

前提：自检通过；还没有标题为"发布清单"的笔记。

- **保存。** 点"新建笔记"，填写标题"发布清单"，点"保存"。结果：出现"已保存"状态，页面标题显示"发布清单"。
- **确认已保存。** 回到列表，再打开这条笔记。结果：标题和正文都还在。
- **CLI 入口。** 运行 `notes create --title "CLI 笔记" --body "来自终端" --format json`。结果：退出码为 0，stdout 里包含新笔记的 ID。
- **证据。** 截取列表页的截图，并保存页面结构快照到 `.verify-evidence/create-note/`。

## 注意事项

- 焦点在输入框里时按 `n`，会输入字符 n，不会新建笔记。
- 只看到"已保存"提示不算证明，必须从列表重新打开这条笔记确认。
- 清理时要删除测试时创建的笔记，但证据要保留。
```
